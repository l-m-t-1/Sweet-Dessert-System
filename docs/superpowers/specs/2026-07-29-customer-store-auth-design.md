# 用户商城与安全认证设计

## 目标

在现有甜品管理后台基础上，增加面向普通用户的独立商城，并建立真实的后端身份认证和角色权限体系，形成以下完整业务闭环：

1. 用户注册并登录。
2. 用户浏览在售甜品并加入购物车。
3. 用户提交订单，系统扣减库存并记录流水。
4. 用户查看或取消自己的待处理订单。
5. 管理员在现有后台管理商品、库存、全部订单和用户状态。

项目继续使用一个 Vue 应用和一个 Spring Boot 应用，不拆分为两个独立前端工程。

## 角色与权限

系统只有两种角色：

- `ADMIN`：系统管理员。保留唯一的默认管理员账号，不提供通过接口创建管理员的能力。
- `USER`：普通用户。所有公开注册的账号都固定为该角色。

权限规则：

| 功能 | 未登录 | USER | ADMIN |
| --- | --- | --- | --- |
| 浏览在售甜品 | 允许 | 允许 | 允许 |
| 注册、登录 | 允许 | 允许 | 允许 |
| 购物车 | 本地浏览器保存 | 允许 | 不作为管理功能使用 |
| 创建订单 | 禁止 | 允许 | 管理后台仍可创建线下订单 |
| 查看、取消本人订单 | 禁止 | 允许 | 可查看和处理全部订单 |
| 分类、甜品、库存管理 | 禁止 | 禁止 | 允许 |
| 用户列表与账号停用 | 禁止 | 禁止 | 允许 |

后端必须执行权限校验，不能只依赖前端隐藏菜单。

## 账号与认证

### 注册

注册表单只包含：

- 用户名
- 密码

规则：

- 用户名去除首尾空格后保存，长度为 3–30 个字符。
- 用户名在数据库中唯一，重复注册返回明确错误。
- 密码长度为 6–72 个字符。
- 注册接口忽略客户端提交的角色，始终创建 `USER`。
- 新用户默认启用。

### 密码

- 使用 BCrypt 保存密码哈希，数据库不再保存明文密码。
- Flyway V4 将现有默认管理员 `admin / admin123` 的明文密码升级为 BCrypt 哈希。
- 登录只使用 BCrypt 校验，不保留明文兼容分支。

### JWT

- 登录成功后返回访问令牌和用户摘要：`token`、`id`、`username`、`role`。
- JWT 包含用户 ID、用户名、角色和签发/过期时间。
- 默认有效期为 2 小时。
- 签名密钥从 `JWT_SECRET` 环境变量或 Git 忽略的本机配置读取，不提交到仓库。
- 前端在 `sessionStorage` 保存令牌和用户摘要，并在 Axios 请求中发送 `Authorization: Bearer <token>`。
- 收到 HTTP 401 时清除登录信息并跳转登录页；HTTP 403 显示无权限提示。

### 账号停用

`user` 表增加 `status` 字段：

- `1`：启用。
- `0`：停用。

每次受保护请求都根据 JWT 中的用户 ID 查询当前账号状态。账号被管理员停用后，即使旧 JWT 尚未过期，也不能继续访问。

管理员不能停用自己的账号。系统不提供删除用户接口，避免破坏订单关联。

## 数据库设计

新增 Flyway V4 迁移：

### `user`

- 将 `username` 设为唯一索引。
- 确保 `password` 长度支持 BCrypt 哈希。
- 增加 `status TINYINT NOT NULL DEFAULT 1`。
- 增加 `create_time` 和 `update_time`。
- 将默认管理员密码更新为 BCrypt 哈希。

### `orders`

- 增加可空字段 `user_id BIGINT`。
- 增加 `idx_orders_user_id_create_time` 索引。
- 增加指向 `user(id)` 的外键。

`user_id` 对旧订单保持可空，保证已有线下订单和演示数据不会丢失。用户端创建的新订单必须写入当前用户 ID；管理员创建的线下订单可以不关联用户。

## 后端接口

### 公开接口

- `POST /api/auth/register`
  - 请求：`{username, password}`
  - 响应：新用户摘要，不自动登录。
- `POST /api/auth/login`
  - 请求：`{username, password}`
  - 响应：JWT 和用户摘要。
- `GET /api/store/desserts`
  - 只返回已上架甜品，支持分页、关键词和分类筛选。
- `GET /api/category`
  - 商城筛选需要公开读取分类；增删改仍仅限管理员。
- `/uploads/**`
  - 保持公开，用于展示甜品图片。

### 普通用户接口

- `GET /api/customer/orders`
  - 只查询当前用户的订单。
- `GET /api/customer/orders/{id}`
  - 只能读取当前用户自己的订单详情。
- `POST /api/customer/orders`
  - 客户名称固定使用当前用户名。
  - 联系电话选填。
  - 总价、商品名称和单价均由后端数据库计算。
- `PUT /api/customer/orders/{id}/cancel`
  - 只能取消当前用户自己的 `CREATED` 订单。
  - 继续复用现有库存返还和流水逻辑。

### 管理员接口

现有管理接口继续保留，并限制为 `ADMIN`：

- `/api/user/**`
- `/api/dashboard/**`
- `/api/dessert/**`
- 分类写操作。
- `/api/orders/**`
- `/api/stock-records/**`
- `/api/upload/**`

用户管理新增：

- `GET /api/admin/users`
- `PUT /api/admin/users/{id}/status`

## 服务层调整

现有订单服务增加明确的调用参数：

- 管理员创建线下订单：`createOrder(request, null, customerName)`。
- 普通用户创建订单：`createOrder(request, currentUserId, currentUsername)`。
- 查询详情和取消操作在服务层校验订单归属，不能只在控制器过滤。

库存扣减、订单取消返还、库存流水和事务边界继续复用现有实现。

## 前端结构

### 公共页面

- `/login`：登录页，增加“注册账号”入口。
- `/register`：仅用户名和密码，并要求再次确认密码。

### 用户端

- `/shop`：甜品卡片列表、搜索、分类筛选、分页、加入购物车。
- `/cart`：修改数量、删除商品、显示预计金额、填写可选联系电话、提交订单。
- `/my-orders`：查看本人订单、展开订单详情、取消待处理订单。

购物车保存在 `localStorage`，刷新页面后仍然存在；提交订单成功后清空购物车。后端仍会重新校验商品状态、实时价格和库存。

### 管理端

现有页面统一调整到：

- `/admin/home`
- `/admin/dessert`
- `/admin/category`
- `/admin/orders`
- `/admin/stock-records`
- `/admin/users`

管理员登录后进入 `/admin/home`，普通用户登录后进入 `/shop`。直接访问不匹配角色的路由时跳转到各自首页。

## 状态与错误处理

- 认证状态封装为单一模块，负责读取、保存和清除 Token。
- Axios 请求拦截器统一添加 Token。
- 注册重名、密码错误、账号停用、库存不足、无权访问订单等错误使用明确中文提示。
- 用户端空订单、空购物车和无搜索结果提供独立空状态。
- 前端不能依据本地角色决定安全结果，本地角色只用于导航显示。

## 测试策略

### 后端

- 注册始终创建 `USER`，密码以 BCrypt 保存。
- 重复用户名注册失败。
- 正确密码登录成功，错误密码和停用账号登录失败。
- JWT 缺失、无效和过期时返回 401。
- `USER` 访问管理接口返回 403。
- `ADMIN` 可以访问管理接口。
- 用户只能查询和取消自己的订单。
- 用户创建订单时客户名称来自 JWT，而非请求体。
- 原有库存扣减、取消返还和流水测试继续通过。
- Flyway 迁移版本唯一且 V4 包含必要字段和索引。

### 前端

- 认证存储和 Axios Token 注入测试。
- 角色路由跳转测试。
- 购物车数量、金额和持久化测试。
- 用户注册、登录、下单和取消订单的关键组件测试。
- 生产构建继续通过。

### 集成验证

使用真实 MySQL 完成一次：

1. 注册普通用户。
2. 登录并获取 JWT。
3. 浏览商城并创建订单。
4. 验证订单关联用户、库存减少且流水生成。
5. 用户取消订单，验证库存恢复。
6. 管理员查看全部订单和用户列表。
7. 停用用户，验证旧 JWT 立即失效。

验证产生的临时用户和订单在测试后清理。

## 不在本阶段范围

- 手机号或邮箱注册。
- 短信、邮件验证码。
- 找回密码。
- 第三方登录。
- 真实支付、退款和配送。
- 多管理员创建与复杂权限配置。
- 将用户端拆成独立前端工程。

这些能力可以后续扩展，但不阻塞当前简历项目形成完整的用户下单闭环。
